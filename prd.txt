# PART 1 — MASTER INSTRUCTIONS FOR THE CODING ASSISTANT

You are acting as a Senior Full-Stack Python Engineer, PDF Processing Specialist, and Technical Architect.

Build a production-oriented web application called **Jain Invitation Personalizer**.

The application will personalize an existing four-page Jain religious invitation PDF.

Only the recipient information on the FIRST page may change. Pages 2, 3, and 4 must retain their original content and visual quality.

The application must support:

1. Single invitation generation using a manual entry form.
2. Bulk invitation generation from an Excel file containing up to 100 recipients.
3. Hindi, English, and mixed-language recipient information.
4. Three independent recipient fields.
5. Optional second and third fields.
6. Automatic text fitting and wrapping.
7. Center-aligned maroon text.
8. Live first-page preview.
9. Direct PDF downloads on mobile devices.
10. Bulk ZIP downloads.
11. Public access without authentication.
12. Deployment to Render.
13. No database and no permanent generated-file storage.

## Critical Development Rules

- Do not redesign or recreate the invitation PDF.
- Never modify the original PDF template in place.
- Do not change the religious text, dates, names, images, graphics, or existing typography.
- Do not use AI image generation.
- Do not use paid APIs.
- Do not introduce unnecessary infrastructure.
- Preserve recipient text exactly as supplied.
- Never automatically add श्री, श्रीमती, जैन, or other honorifics.
- Never automatically translate or transliterate names.
- Ensure correct Devanagari shaping and font embedding.
- Ensure PDF generation works on Render's Linux environment.
- Implement and test one phase at a time.
- Do not claim a phase is complete until its acceptance tests pass.
- Do not assume the exact text coordinates until the original PDF has been inspected.
- If a technical limitation prevents a requirement, explain it and propose the smallest practical alternative before changing the design.

# PART 2 — PRODUCT OVERVIEW

## 2.1 Problem Statement

The user has a finalized four-page invitation PDF for a Jain religious event.

The user needs to invite approximately 100 people, each with different recipient information.

Manually editing the PDF 100 times is inefficient.

The user also wants to generate additional personalized invitations in the future from any mobile phone.

## 2.2 Proposed Solution

Create a publicly accessible web application that allows the user to:

- Enter recipient information manually.
- Preview the personalized first page.
- Generate the complete four-page PDF.
- Automatically download the PDF.
- Upload an Excel file containing up to 100 recipients.
- Generate individual PDFs for every valid Excel record.
- Download all generated PDFs as a ZIP archive.

## 2.3 Product Goals

**Primary goal:** Generate professional personalized invitation PDFs without manually editing the source PDF.

**Secondary goals:**

- Support any modern mobile browser.
- Minimize hosting costs.
- Keep the implementation simple.
- Maintain exact spelling of names.
- Support reusable single-entry and bulk workflows.
- Keep the application maintainable and deployable through GitHub and Render.

## 2.4 Non-Goals

The first release must NOT include:

- User registration or login.
- Payment integration.
- WhatsApp message automation.
- Email sending.
- Dynamic PDF template uploads.
- Multiple invitation templates.
- Online PDF editing.
- AI-based image generation.
- Historical invitation storage.
- Invitation ID tracking.
- Database integration.
- Automatic translation.
- Automatic honorific or surname insertion.
- Changes to pages 2–4.

# PART 3 — FUNCTIONAL REQUIREMENTS

## FR-01: Static PDF Template

The application will use one predefined four-page PDF file.

Expected location:

`assets/invitation.pdf`

The PDF will be bundled with the application during deployment.

Requirements:

- Verify that the template exists during application startup.
- Verify that the PDF contains exactly four pages.
- Detect the dimensions and rotation of the first page.
- Preserve the source PDF's page dimensions.
- Never overwrite the source file.
- Add recipient information only to the first page.
- Retain the original content of all four pages.

The template is changed only through a code/configuration update and redeployment.

## FR-02: Single Invitation Mode

The application must provide a mobile-friendly form with three fields.

### Field 1: Name

- Required.
- Supports Hindi.
- Supports English.
- Supports mixed Hindi and English.
- Supports punctuation and honorifics.
- Must preserve the entered spelling.

Examples:

`श्री सुरेन्द्र कुमार जैन`

`श्रीमती आशा–राजेन्द्र मोदी`

`Mr. Rohit Jain`

### Field 2: Second Line

Optional free-text field.

Can contain:

- Designation.
- Alias.
- Second person's name.
- Relationship information.
- Additional recipient details.

Examples:

`अध्यक्ष, दिगम्बर जैन समाज`

`श्री राजेन्द्र कुमार जैन`

`President, Jain Samaj`

If empty, the line must not occupy vertical space.

### Field 3: City / Location

Optional free-text field.

Examples:

`जबलपुर`

`मोहनगढ़ खास`

`इंदौर, मध्य प्रदेश`

`New Delhi`

If empty, the line must not occupy vertical space.

### Form Behavior

- Generate is disabled when Name is empty.
- Optional fields may remain empty.
- Provide clear validation errors.
- Display loading feedback during PDF generation.
- Support direct download after successful generation.
- Keep the form values after download so users can make corrections.

## FR-03: Recipient Text Formatting

All populated fields must follow the same base typography.

Required formatting:

- Horizontal alignment: Center.
- Vertical alignment: Entire text group centered within a predefined rectangle.
- Text color: Maroon.
- Initial suggested color: `#800020`.
- Font size: Equal for all populated fields.
- Optional lines: Removed from layout when empty.
- Text effects: None.
- Background: Transparent.
- Extra heading: None.

The actual font size and rectangle dimensions must be finalized after PDF inspection.

## FR-04: Dynamic Text Layout Engine

The application must support different name lengths.

Layout algorithm:

1. Read the three input fields.
2. Preserve the original input text.
3. Remove optional empty fields from the layout.
4. Shape the text using a Devanagari-compatible rendering engine.
5. Measure the actual rendered text.
6. Attempt to fit the text at the configured default font size.
7. If the text is too wide, reduce the shared font size.
8. If still too wide, wrap at appropriate word boundaries.
9. Recalculate the total text-group height.
10. Center the entire group vertically.
11. Center every rendered line horizontally.
12. Validate that the group fits inside the configured rectangle.

### Long Name Handling

The system must never silently crop or truncate names.

If the text cannot fit:

- Use the minimum permitted font size.
- Generate a warning.
- Continue processing according to the agreed batch behavior.
- Mark the affected invitation in the generation summary.
- Prefer a visibly readable result; never silently produce clipped text.

If content cannot be rendered safely within the rectangle, return a clear layout error for that record rather than producing a corrupted invitation.

### Shared Font Size

All three fields must use the same font size within a particular invitation.

The font size may vary between different invitations depending on content length.

## FR-05: Hindi and English Rendering

Correct Devanagari rendering is a critical requirement.

Support:

- Hindi names.
- English names.
- Mixed-language names.
- Matras.
- Conjunct characters.
- Unicode punctuation.
- Long and short names.

Test strings must include:

`श्रीमती`

`सुरेन्द्र`

`क्षेत्र`

`प्रज्ञा`

`श्रद्धा`

`जिनेन्द्र`

`श्री 1008`

Use a compatible bundled font such as Noto Sans Devanagari, subject to font licensing and visual validation.

The implementation must use proper complex-script shaping.

**Do not assume that a simple PDF `insert_text()` call provides correct Hindi shaping.**

A viable approach is to use a HarfBuzz-compatible shaping engine through Qt/Pango or another suitable rendering layer and composite the correctly shaped output into the PDF.

Choose a technique that supports both correct visual rendering and the required PDF quality.

Where practical, prefer embedded searchable text. If a rasterized text overlay is necessary for reliable Devanagari rendering, limit rasterization to the personalized text overlay, not the complete PDF pages.

## FR-06: Live Preview

The first page must be displayed in the browser.

Preview requirements:

- Show the original first page.
- Overlay the entered recipient information.
- Update as the user types.
- Maintain correct proportions on mobile screens.
- Support Hindi and English.
- Use the same logical text boundaries as PDF generation.
- Display the full first page, not only the text area.

### Preview Architecture

Use a pre-rendered preview image of the first page.

The browser overlays the text using normalized coordinates derived from the PDF layout configuration.

Avoid sending a backend request for every keystroke.

However, the final PDF renderer is authoritative.

If browser and backend font metrics differ, provide a server-generated verification preview before final generation or adjust the shared rendering strategy.

The final output must match the approved preview within defined visual tolerances.

## FR-07: Single PDF Generation

When Generate is clicked:

1. Validate the form.
2. Send the recipient information to the backend.
3. Load the original PDF template.
4. Apply the personalized text overlay to Page 1.
5. Preserve Pages 2–4.
6. Generate the final four-page PDF.
7. Return the PDF as a downloadable response.
8. Trigger the browser download.
9. Provide a fallback download action when necessary.

Filename format:

`Invitation_<Name>.pdf`

Example:

`Invitation_श्री_सुरेन्द्र_कुमार_जैन.pdf`

Use filesystem-safe filename handling without changing the displayed recipient name.

## FR-08: Bulk Excel Mode

The application must accept Excel `.xlsx` files.

Required column headers:

| Name | Second_Line | City |
|---|---|---|
| श्री सुरेन्द्र कुमार जैन | अध्यक्ष, जैन समाज | जबलपुर |
| श्री भूपेन्द्र जैन | | सागर |
| श्रीमती आशा–राजेन्द्र मोदी | | इंदौर |

### Processing Rules

- Maximum 100 data rows per batch.
- Name is mandatory for generating an invitation.
- Second_Line is optional.
- City is optional.
- Skip rows with empty Name.
- Preserve text exactly.
- Do not modify the uploaded Excel file.
- Do not perform automatic spelling corrections.
- Treat formula cells carefully; do not execute formulas or macros.
- Reject unsupported or malformed Excel files.
- Prevent excessively large uploads.

The maximum batch limit must not be bypassed by adding blank rows or unusual spreadsheet structures.

## FR-09: Bulk Preview

Before generating all PDFs:

- Parse and validate the Excel file.
- Show total rows and valid recipients.
- Display 3–5 representative sample invitations.
- Include long-name cases where available.
- Display validation warnings.
- Provide Generate All confirmation.

## FR-10: Bulk PDF Generation

For each valid recipient:

1. Load or safely reuse the immutable original template.
2. Generate a new personalized PDF.
3. Preserve all four pages.
4. Assign a unique filename.
5. Add the PDF to a ZIP archive.

### Duplicate Filenames

If two recipients produce the same filename, use:

`Invitation_श्री_सुरेन्द्र_जैन.pdf`

`Invitation_श्री_सुरेन्द्र_जैन_2.pdf`

`Invitation_श्री_सुरेन्द्र_जैन_3.pdf`

Never overwrite another recipient's output.

## FR-11: Bulk ZIP Download

The final ZIP should contain all successfully generated individual PDFs.

Example:

`Invitations_Batch.zip`

ZIP structure:

`Invitation_श्री_सुरेन्द्र_जैन.pdf`

`Invitation_श्री_भूपेन्द्र_जैन.pdf`

`Invitation_श्रीमती_आशा_राजेन्द्र_मोदी.pdf`

Use standard ZIP compression compatible with Android, iOS, macOS, and Windows.

## FR-12: Generation Summary

After bulk processing, display:

- Total Excel rows.
- Valid recipients.
- Successfully generated PDFs.
- Skipped rows.
- Records with layout warnings.
- Failed records.
- ZIP download status.

Example:

Total rows: 100  
Generated: 97  
Skipped: 2  
Failed: 1  
Layout warnings: 3

Warnings must not stop unrelated valid records from processing.

## FR-13: File Storage

Generated files must not be permanently stored on the server.

Requirements:

- Use in-memory processing where practical.
- Use temporary files when necessary.
- Remove temporary files after processing.
- Do not store recipient names in a database.
- Do not expose generated files through public static directories.
- Do not rely on Render's local filesystem for persistence.

The original PDF template remains bundled with the application.

## FR-14: Public Access

The website must be accessible without login.

Requirements:

- Public HTTPS URL.
- Mobile and desktop access.
- No account creation.
- No authentication for MVP.
- Basic rate limiting.
- Excel upload validation.
- Maximum 100 recipients per batch.
- Request size limits.
- Safe error handling.

# PART 6 — API DESIGN

Use `/api` as the API prefix.

## Endpoint 1: Health Check

`GET /api/health`

Purpose:

Verify application availability and template readiness.

Expected response:

```json
{
  "status": "ok",
  "template_loaded": true
}
```

Do not expose internal server paths.

## Endpoint 2: Template Preview

`GET /api/template/preview`

Returns a preview image of the original first page.

The image must be generated from the actual bundled PDF.

## Endpoint 3: Layout Configuration

`GET /api/template/layout`

Returns public rendering configuration required for the browser preview.

Example:

```json
{
  "page": 1,
  "coordinate_system": "normalized",
  "text_box": {
    "x": null,
    "y": null,
    "width": null,
    "height": null
  },
  "alignment": "center",
  "vertical_alignment": "center",
  "color": "#800020",
  "font_size": null,
  "minimum_font_size": null
}
```

The null values must be replaced after actual PDF calibration.

## Endpoint 4: Single Generation

`POST /api/invitations/single`

Request:

```json
{
  "name": "श्री सुरेन्द्र कुमार जैन",
  "second_line": "अध्यक्ष, जैन समाज",
  "city": "जबलपुर"
}
```

Response:

- `application/pdf`
- Four-page personalized PDF.
- Download filename in the Content-Disposition header.

## Endpoint 5: Bulk Validation

`POST /api/invitations/bulk/validate`

Input:

Excel `.xlsx` file.

Response:

- Total rows.
- Valid records.
- Skipped records.
- Warnings.
- Representative preview records.

No permanent file storage.

## Endpoint 6: Bulk Generation

`POST /api/invitations/bulk/generate`

Input:

Excel `.xlsx` file.

Response:

- `application/zip`
- Individual four-page PDFs.

Generation summary can be included in the ZIP as a small JSON or text manifest, or communicated through appropriate response metadata.

Do not require a persistent job ID.

For Render's free-tier limits, benchmark the synchronous approach first. If it cannot reliably process 100 records, propose a stateless chunked-download workflow before introducing a database or persistent job queue.
